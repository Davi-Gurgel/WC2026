## Findings considered and rejected

(Recorded so nobody re-audits them.)

- **Micro-perf**: group `filter` inside `initializeTournament`'s 12-iteration loop, `decodeURIComponent` try/catch per team lookup, eager `maxPlayerStrength` computation — one-time or per-navigation microsecond costs; not worth doing.
- **Split the monolithic tournament context / selector hooks**: every simulator page legitimately re-renders on tournament state changes; no measurable cost at 6 pages.
- **Move team-JSON validation to build time / out of the client bundle**: the client-side simulation needs the full roster at runtime, and `lib/teams.test.ts` already fails the gate on invalid JSON; the once-per-session Zod parse is cheap.
- **"Layering violation" (UI importing `scoreDisplay` from `@/lib/tournament`)**: that's the documented barrel-import convention — by design.
- **UI/page test coverage**: pages are thin wrappers over a tested engine; not worth it at this size.
- **lucide-react version lag**: a `pnpm up` chore, not a plan.
- **Storage migrations (versioned state upgrades)**: contradicts the deliberate "discard, don't migrate" convention in AGENTS.md; revisit only if shared/exported states (plan 009) make saved data precious.
- **CSP `unsafe-inline` tightening (audit finding #8, MED confidence)**: deferred without a plan — Next.js's inline bootstrap scripts make nonce-based CSP a framework-level spike with low payoff for a static client app with no user-generated content. Revisit if the app ever renders external content.
- **TournamentProvider mid-tournament hydration test (audit finding #10)**: folded into plan 003's philosophy but not planned separately; add a case to `components/TournamentProvider.test.tsx` opportunistically when next touching the provider.
- **Storage guard country-code validation (audit finding #9)**: not rejected — folded into plan 009 Step 1 as the hardening prerequisite for import.
